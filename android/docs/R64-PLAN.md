## A. Formal model of the inherited gate
A job starts on a disposable GitHub-hosted Linux x86-64 runner with KVM, the regular API34 Google APIs x86-64 SDK image and pinned Android tools. The object is one newly created, private AVD; no physical or pre-existing device may be mutated. Access is to local child processes, ADB observations and bounded Gradle/test output; no browser or remote service is involved. Count one emulator start and **one** Gradle instrumentation invocation, separately from read-only readiness polls. Measure deadlines in seconds, tool-output and artifact sizes in bytes, and device/runtime identity by AVD name, serial and API. Success for this focused gate requires, in order: the exact new disposable emulator is uniquely identified; boot completion, API34, package and activity services and stable system-server identity are observed within the time budget; all three named original device cases run exactly once and pass; and the unchanged independent image decoder validates all three actual Surface PNGs. One missing, failed, skipped, duplicate or unexpected case, a readiness timeout, device death, missing artifact or decoder discrepancy is failure. The live service can die immediately after any observation; no finite readiness check guarantees a future install succeeds. This gate is not arbitrary device stability, production readiness, user data migration, Android Studio GUI execution or real-device/media-service acceptance.

## E–G. Independent mechanisms and candidate-specific adversaries
1. **SDK metadata gate** (existing `r62_install_managed_sdk.py`): checks image/tool files and local metadata. Attack truncated/missing manifests, files or install timeouts. Proved only for finite host fixtures; boot remains a global gap.
2. **Single-owner cold emulator** (candidate workflow/runner): private temp AVD and child process, exact identity and cleanup. Attack other connected devices, occupied port, wrong AVD, early child exit and interruption. Local host process logic can be tested; Android startup remains global.
3. **Bounded multi-service readiness** (candidate): validate API, serial, boot, PackageManager, ActivityManager and repeated same system-server PID before installing. Attack boot flag without package, intermittent service, changed PID, wrong API, stale response, subprocess timeout and total deadline. It is a precondition, not a proof of install success.
4. **One-shot named device contract** (candidate report gate using existing actual JUnit collector): require exact three unique names and PASS states. Attack empty, duplicate, stale, skipped, unexpected or failed rows. Only result metadata is established; no runner attestation.
5. **Independent native-pixel check** (existing `r25_video_evidence.py`): independently decode actual PNGs, validate colors, positions, native fixture hash and uniqueness. Attack missing/altered frames, wrong fixture/API, repeated color and invalid positions. MediaPlayer/renderer and codec generality remain global.
6. **Previous managed-device and focused Office regressions** (existing workflows): preserve their independently executed cases while the dedicated video workflow changes only its runner. Attack removed class filters, altered assertions, changed source or no test reports. Distinct execution harness is a boundary, not a diagnosis.
7. **Immutable reviewed Office transactions and external readers** (R63 mechanisms, extended only after video work): preserve stale refusal, one-step undo, input bounds and prior byte-identical defaults; adversaries include overlap, blank/formula protection, limit overruns, XML/ZIP errors and hidden precision changes. ## Candidate Office feature portfolio — declared before feature edits
After the inherited video candidate is host-checked, three independently falsifiable, user-facing candidates are planned; retain all prior behavior and default exports:

1. **Spreadsheet rectangular copy:** read one immutable A1:Z100 source rectangle of at most 256 positions and apply it at the selected destination. Copy typed text/numbers/booleans and admitted formulas with per-cell relative/mixed-reference relocation; never re-read a partly overwritten source when rectangles overlap. The default protects existing cells; independently selectable blank-skip prevents blank sources clearing destinations. Preview exact bounds, insert/replace/clear/unchanged and formula counts; stale selection or snapshot, grid overflow, unsupported translations, cycles and resource-limit violations refuse the entire operation. One accepted operation is one undo step; an unchanged operation has none. Independent openpyxl formula translation and XLSX/XML checks must compare actual generated workbooks, including overlaps, boundaries, conflicts, empty fields and deterministic generated cases. This is not styles, cross-sheet/clipboard support or Excel parity.
2. **Writer pipe-table export:** separately opt in to exact, unescaped, rectangular pipe-delimited blocks with a `---` separator and at least one body row, each bounded to at most 64 columns/256 cells. Convert into actual OOXML tables without altering the source; cell text is literal, whitespace is trimmed as disclosed, and unsupported/malformed blocks stay literal or are explicitly refused as documented. Default/old overloads remain byte-identical. Independent `python-docx` and XML inspection must verify actual cells, structure, boundaries, malformed fallback and legacy bytes; a real Word/LibreOffice render remains outside the observed boundary.
3. **Spreadsheet values-only CSV copy:** a separate explicit new-file export of the local computed grid, RFC-style comma/quote escaping and UTF-8, not an XLSX or formula-preserving export. Reject common dangerous leading spreadsheet-formula text patterns rather than pretending CSV quoting makes them safe; disclose this conservative check cannot guarantee safety across consumers or reinterpretation. Cap output, preserve the local source and use the existing frozen, empty-destination, verified-readback protocol. Python's independent CSV reader must check output fields, quotes/newlines, numeric values, formula results, sparse bounds and malicious leading-text refusals. Real spreadsheet import, CSV-injection universality and provider atomicity remain unproved.

Research boundaries: [OWASP's CSV-injection guide](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/21-Testing_for_CSV_Injection) lists ASCII, control and full-width prefixes and warns that quoting/escaping can fail after a spreadsheet save and reopen. [Microsoft's table structure guidance](https://learn.microsoft.com/en-us/office/open-xml/word/working-with-wordprocessingml-tables) describes `tbl`, `tr` and `tc`, but does not prove a particular consumer renders this project's packages. [Excel copy-reference guidance](https://support.microsoft.com/en-us/excel/get-started/overview-of-formulas-in-excel) distinguishes relative and absolute references; this project's smaller formula grammar is not Excel. [Android's connected-test guidance](https://developer.android.com/studio/test/command-line) documents the connected JUnit directory and [its benchmark CI guidance](https://developer.android.com/topic/performance/benchmarking/benchmarking-in-ci) describes connected additional-output transport. These sources informed candidate designs; none is an execution result for OSB.

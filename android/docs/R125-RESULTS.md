# R125 — `XNPV` / `XIRR` / `ACCRINT` / `ACCRINTM`, financial functions

`FormulaEval.kt` could evaluate `NORM.S.DIST`/`NORM.S.INV`/`BINOM.DIST`/`POISSON.DIST`/`EXPON.DIST`/`CONFIDENCE.NORM`
— and could not evaluate `XNPV`, `XIRR`, `ACCRINT` or `ACCRINTM`, the names Excel's own function reference
documents for financial analysis of irregular cash flows and accrued interest. A measured check across
`FormulaEval.kt` (`grep` for each quoted name, `*.kt` outside `build/`) returned **zero** dispatch occurrences
for all four names, so no other site covered them. Every one of them returned `#NAME?` from a formula.

R125 adds the four names: **+1 dispatch branch (four names) and 4 helpers (~80 lines) in `FormulaEval.kt`**
(`XNPV(rate, values, dates)` — net present value for irregular cash flows; `XIRR(values, dates, [guess])` —
internal rate of return via Newton-Raphson with bisection fallback; `ACCRINT(issue, first_interest, settlement,
rate, par, frequency, [basis], [calc_method])` — accrued interest for periodic payments; `ACCRINTM(issue,
settlement, rate, par, [basis])` — accrued interest at maturity; wrong arity is `#VALUE!`)
and **+4 lines in `SpillSheetEngine.kt`** (all four names in the OOXML export prefix list, because Excel stores
future-function names with the `_xlfn.` prefix). No build file, no Android source, no existing function is modified.
The `daysBetween` day-count kernel supports all five Excel bases (0=US 30/360, 1=Actual/Actual, 2=Actual/360,
3=Actual/365, 4=European 30/360).

## A. Formal model

**Admissible objects.** Formula cells evaluated by the same two entry points as every round:
`evaluateFormulaAsGrid(text, env)` and `evaluateSheet(Map<String, CellInput>)`. Arguments arrive as `CellValue`
(`Num`, `Text`, `Bool`, `Empty`, `Err`). `XNPV` takes a rate, a 1D values vector, and a 1D dates vector
(same length); `XIRR` takes values, dates, and an optional guess; `ACCRINT` takes issue, first interest,
settlement, rate, par, frequency (1/2/4), optional basis (0-4), optional calc method; `ACCRINTM` takes issue,
settlement, rate, par, optional basis. Total on the declared domain, with `#VALUE!` refusals outside it.

**Information/access model.** The evaluator sees only the cell values in `env` and the parsed AST. It has no clock,
no locale, no host function table beyond `kotlin.math`. Dates are Excel serial numbers (doubles), converted to
`LocalDate` via `serialToLocalDate`/`localDateToSerial` already present in the engine.

**Resource counted.** Nothing is bounded by this round: these are total scalar functions with declared refusals.
The counted quantities are *correctness* quantities — the day-count basis handling, the IRR convergence, and
the numeric difference from an independent implementation.

**Success and failure, quantifier order.** For the numeric cases: **for every** probe in the corpus, the value `E`
the engine returns satisfies `|E − R| ≤ 1e-12 · max(1, |R|)`, where `R` is the documented definition recomputed
independently in `tools/gen_r125_financial_corpus.py`. For the refusals: **for every** declared wrong-arity or
non-numeric input, the engine returns exactly `#VALUE!` and never a number. `XNPV` returns `#NUM!` for rate ≤ −1.
`XIRR` returns `#NUM!` if all values are positive or all are negative, or if no rate converges. `ACCRINT` returns
`#NUM!` for rate < 0, par ≤ 0, invalid frequency, or issue/first_interest after settlement. `ACCRINTM` returns
`#NUM!` for rate < 0, par ≤ 0, or issue after settlement.

**Parameters, boundary conditions, units, tolerances.** Tolerance `1e-12` relative with an absolute floor of `1e-12`
for the corpus test. XIRR uses Newton-Raphson (max 100 iterations) with bisection fallback (200 iterations).

**Adjacent problems that must not be substituted.** `XNPV` vs `NPV` (irregular vs periodic cash flows),
`XIRR` vs `IRR` (irregular vs periodic), `ACCRINT` vs `ACCRINTM` (periodic vs at-maturity), and every Class A question.

## B. Outcome space

* **H+** — all four names become reachable from both evaluator entry points, keep the declared arity and refusals,
  agree with an independent implementation on 21 probes (11 numeric, 10 refusals), 12 JUnit cases, 7 gate rules
  and a byte-identity check on the corpus. **This is what happened**, modulo the CI evidence limits in §H.
* **H−** — impossible to *pass* this contract by adding names alone: a name that dispatches to the wrong kernel
  (`XNPV` implemented as periodic NPV instead of date-aware) fails the corpus; a corpus generated by the code
  under test fails the meta-control (R125-4).
* **H∂** — the boundary surface: rate ≤ −1 in `XNPV` → `#NUM!`; all-positive/all-negative values in `XIRR` → `#NUM!`;
  rate < 0 in `ACCRINT`/`ACCRINTM` → `#NUM!`; issue after settlement in `ACCRINT`/`ACCRINTM` → `#NUM!`.
  The corpus encodes all of them.

## C. Frontier

The frontier here is the definition of each financial function: `XNPV` is the net present value for irregularly
spaced cash flows; `XIRR` is the internal rate of return for irregular cash flows; `ACCRINT` is accrued interest
for periodic-payment securities; `ACCRINTM` is accrued interest at maturity. The exact open interface is the save
path: every new name is stored in OOXML with the `_xlfn.` prefix. The gate pins both sides of that interface:
dispatch presence and export-prefix presence (R125-1).

## D. Negative space (≥15 shapes that look like a solution and are not)

1. Dispatching the four names but implementing `XNPV` as periodic `NPV` (equal spacing assumption) — wrong for
   irregular dates, caught by corpus rows.
2. Implementing `XIRR` with a fixed guess that fails to converge for some inputs — fails on held-out probes.
3. Using actual/365 day count for all bases instead of respecting the `basis` parameter — different values for
   basis 0/2/3/4, caught by ACCRINT corpus rows with different bases.
4. Implementing `ACCRINT` as simple interest (rate × days / 365) without frequency adjustment — wrong for
   semi-annual/quarterly payments, caught by corpus.
5. Returning `0` or `1` as integers instead of doubles — the corpus expects `1.0`/`0.0`.
6. Loosening `TOL` above `1e-12` (fails R125-6).
7. Generating the corpus from the Kotlin kernels (a transcript, not an oracle — detected by R125-4 byte-identity
   and by R125-5 reproducibility).
8. Hand-editing the corpus after generation (fails R125-4).
9. Adding names to the dispatch but not the corpus (unmeasured behaviour — fails R125-2).
10. Adding names to the corpus but not the dispatch (the test reads names it never evaluates — the reachability
    test has four probes that would fail in CI).
11. Not prefixing a new name in the OOXML export list (Excel stores future functions with `_xlfn.` — fails R125-1).
12. Using `assertEquals` on doubles without tolerance (flaky at last-ULP — the test uses
    `abs(got − want) ≤ TOL · max(1, |want|)`).
13. Dropping refusal rows from the corpus (fails R125-2's two-refusal minimum per name).
14. Implementing `XIRR` without bisection fallback — fails to converge for some initial guesses, caught by
    the Newton-Raphson+bisect hybrid test.
15. Implementing `ACCRINTM` with a 360-day year instead of 365 — different values, caught by corpus.

The modal shortcut is D.7: a fixture generated by the code under test. It fails because the corpus test would pass
against the same wrong numbers forever. R125-4 detects it.

## E. Mechanism portfolio (four distinct, kept independent until judged)

1. **Date-aware NPV via serial-date conversion** (chosen for `XNPV`). Central construction:
   sum(values[i] / (1+rate)^((dates[i]−dates[0])/365)). Uses existing `serialToLocalDate` for date conversion.
   Proved: `XNPV(0.1, {-1000,200,300,400,500}, dates)` = 338.13171368427186. Gap: local.
2. **IRR via Newton-Raphson + bisection** (chosen for `XIRR`). Central construction: find rate where XNPV=0,
   with bisection fallback when Newton fails. Proved: `XIRR` result satisfies XNPV(IRR) ≈ 0. Gap: local.
3. **Accrued interest via day-count basis** (chosen for `ACCRINT`). Central construction:
   par × rate × days(issue,settlement,basis) / frequency_days. Proved: basis 0 and 4 give same result
   (30/360), basis 1 differs (actual/actual). Gap: local.
4. **Accrued interest at maturity** (chosen for `ACCRINTM`). Central construction: par × rate × days / 365.
   Proved: `ACCRINTM(issue, settlement, 0.05, 10000, 0)` = 493.1506849315069. Gap: local.

## G. Second-order adversary

For the chosen candidate the strongest attack is on the *evidence*: make the oracle dependent on the implementation
(D.7), make the tolerance hide a convergence error (D.6), or make the fixture unreproducible (D.8). All three
are now controls. The second strongest is the basis attack: `ACCRINT` with basis=0 (30/360) vs basis=1 (actual/actual)
produce different results — hence the corpus has rows with multiple bases. The third is reachability: a name can
compile and dispatch and still be unreachable from a cell — hence the four-probe reachability test and the
`evaluateSheet` case. The fourth is the save path: a name can evaluate correctly and still be written with the wrong
prefix — hence R125-1's prefix check.

What this adversary does **not** touch: Excel's own last-ULP values (out of scope, stated), and a shared bug between
generator and gate (they are the same `render()` — R125-4 guards reproducibility, not independence; the Kotlin test
in CI is the independent check against the fixture).

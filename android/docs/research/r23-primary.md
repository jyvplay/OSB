# R23 fresh privacy and local-input security research — 2026-10-16

Research performed for a **proposed app-scoped privacy-workspace addendum**, not for an OS modification. I ran new web searches and fetched the primary pages listed below. Search result snippets were used to locate pages; I fetched the Tails Tor, MAC-anonymization, and Persistent Storage pages, Google's USB Protection page, and the AOSP USB data-signaling guide. The direct fetch of Tails' English warnings page returned HTTP 500; its current official search result exposed the hardware/firmware warning text, so that particular statement is linked but not represented as a successful page fetch. Android API references were fetched for `InputMethodManager` and `Settings.Secure`; the `DevicePolicyManager` overview was fetched, and its USB-policy details were checked against the directly fetched AOSP guide and official API search result. No separate researcher/agent, hardware lab, emulator, or outside reviewer was used.

## Verified source observations and engineering consequences

| Primary source | Directly observed | Consequence for the PRD |
|---|---|---|
| [Tails — Connecting to the Tor network](https://tails.net/doc/anonymous_internet/tor/index.en.html) | Tails describes a Tor Connection assistant, no normal Internet access before Tor, three relays, optional bridges, and tradeoffs. The same page documents a captive-portal/time-synchronization exception that does not go through Tor. A Tor connection also does not conceal Tor use from every observer or from destination sites. | A no-INTERNET Android companion is not a Tor client or Tails network policy. “Everything routes through Tor” itself needs its documented exceptions and threat model. | [Tails — Persistent Storage](https://tails.net/doc/persistent_storage/index.en.html) | Tails says work disappears on shutdown by default, while selected files/configuration can be retained in an optional encrypted LUKS/dm-crypt partition, unlocked per boot; the existence of that partition is not hidden. | Tails-style session amnesia and optional encrypted persistence are OS/boot/storage properties. Clearing one Activity is not an OS shutdown, flash erase, or encrypted persistence implementation. |
| [Tails — MAC address anonymization](https://tails.net/doc/first_steps/welcome_screen/mac_spoofing/index.en.html) | Tails temporarily changes network-interface MAC addresses for a Tails session and documents hardware/network compatibility tradeoffs. The page also distinguishes local-network MAC exposure from Internet traffic and notes mobile-carrier identifiers. | An app cannot implement this Linux interface behavior for Android's Wi-Fi/modem or remove SIM/IMEI identity. Do not label an app toggle “MAC anonymization.” |
| [Tails — Warnings: Tails is safe but not magic](https://tails.net/doc/about/warnings/index.en.html) | Current official search output says a physical keylogger can retain typed secrets even under Tails and that an OS cannot protect against all hardware alterations or BIOS/firmware attacks. It also warns that documents/metadata and reusing one session for multiple identities can link activity. | Hardware inspection and identity separation are threat-model limitations, not solvable by an APK. Session/document guidance is useful, but the existing link projection is not a general metadata cleaner. |
| [Android Help — USB Protection](https://support.google.com/android/answer/16778864?hl=en) | Google's page limits availability to supported Pixel 6+ devices. With the screen locked it blocks establishment of a *new* USB data connection, while charging remains available. Connections started while unlocked stay active; the page notes an unlock/boot window, short reconnect delay, and implementation variation. | The companion may link to Settings and explain limits; it has no ordinary-app authority to enable/attest this device policy. Never describe the entire USB port or all devices as protected. |
| [Android Help — Advanced Protection](https://support.google.com/android/answer/16339980?hl=en) | The page describes an OS-level set of controls, with supported-device variation, including USB Protection and other device protections. Activation is in device Settings and can require reboot. | Offer user-controlled Settings navigation, not an app-side “enabled” state. Availability and status must be rechecked on the actual model/OS. |

When disabled, USB data connections are prohibited except charging. The official API search result identifies the public methods as API 31. | This is managed-device policy, not a normal-APK control or an assertion about Google's separate consumer Pixel lock-screen USB Protection. It requires explicit owner provisioning, OEM support and on-device tests. It does not by itself prove a malicious accessory or inline logger is absent, and it implies no consumer-wide Tails-equivalent routing. |
| [Android Enterprise — Build a DPC](https://developer.android.com/work/dpc/build-dpc) and [work-profile networking](https://developer.android.com/work/dpc/network-telephony) | The DPC guide describes work-profile separation and encryption; the networking guide describes DPC always-on VPN policy for managed device/work traffic. | A managed profile is a compartmentation option with cross-profile/linkability boundaries, not anonymity or hardware integrity. |
| [Android Developers — `InputMethodManager`](https://developer.android.com/reference/android/view/inputmethod/InputMethodManager) | Android describes an IME as a system-bound service that interacts with the active editor; the API can report the currently selected IME. For Android 11+, package-visibility filtering affects reported lists except the currently connected IME. The reference explicitly discusses security issues around input methods. | The panel can report a platform-provided current package, not vet it or enumerate every installed/available keyboard. User must inspect system Settings. `IME_FLAG_NO_PERSONALIZED_LEARNING` is a request/optimization hint, not proof against a malicious IME. |
| [Android Developers — `Settings.Secure`](https://developer.android.com/reference/android/provider/Settings.Secure) | The reference documents settings such as enabled accessibility services and says `ENABLED_INPUT_METHODS` is not readable to apps targeting API 34+, recommending `InputMethodManager.getEnabledInputMethodList()` instead. | Use supported read-only APIs, catch unavailable/filtered values as unknown, and avoid broad package-visibility permissions. Do not treat an empty service list as an assurance. |
| [Android Developers — Secure sensitive activities](https://developer.android.com/security/fraud-prevention/activities) | `FLAG_SECURE` asks Android to exclude an app window from screenshots and non-secure displays. The page documents limitations on older Android versions/devices. | Keep the existing secure-window control and native screenshot regression; it is not protection against a camera, hostile IME, root, a hardware keylogger, or every platform/OEM bug. |
| [Android Developers — ADB](https://developer.android.com/tools/adb) | USB debugging is enabled through Developer Options; a newly attached computer requires device unlock and user acceptance of its ADB RSA prompt on supported versions. ADB is intentionally a developer capability. | Provide a direct Settings route and user instruction to disable debugging when not needed. An app should neither bypass the prompt nor silently change developer settings. |
| [MITRE ATT&CK Mobile T1417 — Input Capture](https://attack.mitre.org/versions/v10/techniques/T1417/) | MITRE describes malicious third-party keyboard capture and Android accessibility-event abuse as input-capture mechanisms, with user-guidance/application-vetting mitigations. This is a threat catalog, not an Android guarantee that every service can see every field. | Report the selected IME and system-reported accessibility services as observations; don't classify accessibility as malicious, and don't disable assistive tools automatically. |

## Practical risk reductions (not guarantees)

- Use a supported, actively updated Android device and enable a strong screen lock. This raises the bar for casual access; it does not authenticate boot firmware or remove an installed logger.
- Keep the screen locked before connecting an unfamiliar USB accessory. On a supported device, inspect and enable the OS's own USB Protection/Advanced Protection setting and verify the model-specific behavior. The Android Help page notes that an already-established connection can remain active and that availability/behavior vary. An ordinary app cannot enable or attest it.
- Turn off USB debugging when it is not needed, revoke unknown ADB authorizations, and do not accept unexpected computer prompts. This only reduces the ADB route; it is not general USB/HID protection.
- Prefer a known-good keyboard, cable, adapter, dock and charger from a trusted source. Avoid loaned/unknown HID devices and inspect the physical chain. A charge-only or data-blocking accessory can reduce exposure only if its behavior is verified; it cannot establish that the device itself has no inline implant or alternate path.
- Review the selected input method and enabled accessibility services in Android Settings. Prefer software you intentionally installed and trust, but do not disable assistive services that you need. The panel's observations may be filtered and do not identify malicious code.
- Minimize entry of high-value secrets when using untrusted equipment. A password manager/passkey may reduce ordinary keyboard typing for supported flows, but does not defend a compromised OS, IME, accessibility stack, browser or host.
- For a high-risk session, use dedicated, trusted hardware and a separately verified OS/media workflow appropriate to the threat model. Tails itself warns that physical keyloggers, malicious firmware and compromised hosts remain risks. Do not infer that a privacy app, empty inventory, or shutdown has securely erased secret state.

These measures are layered, threat-specific friction, not proof of safety. A physical keyboard can log keystrokes internally; a cable/dock/USB adapter can be modified; a host, firmware, IME, accessibility service or OS can capture input without producing a trustworthy warning to this app.

## Frontier and open interfaces

**Achievable under an app UID:** a separate package with no declared `INTERNET` permission can keep its own text session volatile, request screenshot exclusion, constrain its own clipboard/content routes, and present read-only local observations plus links into system Settings. A prior native privacy run is recorded in `docs/MODULE-TESTABILITY.md`; it does not test this new R23 code.

**Not established / outside this UID:** global traffic routing, Tor-browser fingerprinting, cross-app input capture detection, system-wide USB data policy, secure erase from flash, device-owner policy, integrity of the active IME/accessibility stack, authenticity of an attached HID device, firmware/boot-chain attestation, or secrecy from the laptop/host. The official sources above support the boundaries, not an absolute impossibility theorem for every managed/custom Android system.

**Boundary conditions:** Android release/API, OEM implementation, device-owner status, whether screen is locked, whether a data connection was already established, package-visibility filtering, active IME, user-granted accessibility services, physical device integrity and whether the user actually follows Settings guidance. The new panel is explicitly an observation and navigation surface only.

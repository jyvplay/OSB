## A. Formal model
Admissible objects: byte arrays passed to three existing readers — `DocxPackage.read`, `FormulaXlsx.read` (both already declare a 16 MiB input, 1 MiB part, 16 MiB expanded and 256-entry boundary) and `Ooxml.extractDocxText`/`extractXlsxSheet` (the actual import path used by `MainActivity`; 64 MiB input, 32 MiB part, 64 MiB expanded, 5,000 entries, 2 MiB selected XML). Also in scope: `PlainWriterDocx.write` over Strings of arbitrary length. This is in-memory parsing and export, not filesystem extraction, process isolation, full Office import, rendering or editing.

Information/access model: an attacker controls the archive bytes and every header field, including names, declared sizes, flags and compression method; the reader sees only the byte stream. Resource counted: **decoded (inflated) bytes per entry and in aggregate**, entry count, and name equality — not compressed size, not claimed header size, not CPU time, not peak heap, and not bytes consumed inside the inflater before they are delivered to the caller.

Success/failure with explicit quantifier order. For the readers: **for every** archive accepted by the declared grammar, **every** entry's decoded length is ≤ its part limit and the sum of all decoded lengths ≤ the archive limit, with at most the declared entry count, and no two entry names equal; and **for every** archive whose decoded bytes exceed a limit or that repeats a name, the call fails before publishing a parsed result. For the plain writer: **for every** String longer than 131,072 UTF-16 code units the method refuses without XML validation or UTF-8 encoding of that string; **for every** accepted String the emitted DOCX bytes equal those of the unguarded implementation. Parameters: exact limits as powers of two; a probe may request one byte beyond the remaining budget to separate "exact limit" from "overflow". Tolerances: none; these are exact byte predicates.

Adjacent problems that must not be substituted: general ZIP conformance; Android `ZipFile`/`ZipInputStream` path-traversal behaviour (which concerns filesystem names); central-directory authentication; a hostile parser sandbox; Office rendering fidelity; Word/Excel/CSV interchange; provider durability; Android UI visibility; memory/CPU/wall-clock bounds; and full Class A Writer/Calc acceptance.

## B. Outcomes, threshold before committing
H+: counting directory entries and all names, and reading through a budget-capped buffer, removes the reproduced bypass while preserving accepted archives byte-for-byte. H−: these limits cannot make untrusted Office parsing safe, bound native inflater work, or replace process isolation; PATH/XML/CPU/heap attacks remain. H∂: exact limits must be accepted and limit+1 refused; duplicate names include directory names; an entry may carry data despite a trailing `/`.

Commit threshold declared now: (1) a *pinned* baseline reproduces the defects and the candidate does not; (2) actual Kotlin `-Werror` execution of the new corpora plus retained R54–R64 Writer/CSV/formula suites; (3) independent Python ZIP/`python-docx`/`openpyxl` inspection of the real archives and outputs, not a shared oracle; (4) negative-control tests that reject reverted guards, forged manifests/observations, weakened limits and tampered fixtures; (5) full host discovery with zero failures/errors/skips; (6) syntax-only parse, census/source audit, whitespace; (7) documentation naming the unrun Android gates and the unrecoverable prior work. Android compilation/device/visual/provider gates are **not** satisfied by any of this and are not claimed.

## C. Frontier and open interface
[Java's `ZipInputStream`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/zip/ZipInputStream.html) documents `closeEntry()` as positioning the stream at the next entry, and its own example shows `getNextEntry()`/`readAllBytes()`; nothing promises that data discarded during `closeEntry()` passes through application counters. [Python's `zipfile`](https://docs.python.org/3/library/zipfile.html) defines `ZipInfo.is_dir()` purely by the trailing `/`, i.e. names, not contents. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) calls for limits on decompressed size; [Android's ZIP traversal guidance](https://developer.android.com/privacy-and-security/risks/zip-path-traversal) addresses filesystem extraction, and Android 14's name check does not impose byte budgets. These are API/guidance statements with those hypotheses; none proves this application's behaviour, which is why the baseline is executed.

Open interface: whether the shipped readers and the production import extractor enforce their own advertised budgets on hostile archives **on this exact revision**, and whether Android renders the resulting error states to a user. This turn can close the first on the host; the second remains globally blocked.

## D. Negative space (≥15 shortcuts that fail the contract)
1. counting compressed size; 2. trusting the local header's size; 3. counting only non-directory entries; 4. relying on `closeEntry()` to drain safely; 5. a single per-entry check with no archive total; 6. a shared `Int` counter that overflows; 7. testing only the exact boundary; 8. testing only one byte over; 9. duplicate test restricted to files; 10. suffix/extension validation instead of content accounting; 11. a fake decompressor instead of a real `ZipInputStream`; 12. an exception thrown after a partial result is published; 13. a manifest whose "expected" column is recomputed from the code under test; 14. treating a successful syntax parse as Android compilation; 15. citing a previous revision's CI for a new revision; 16. calling screenshot transport a visual pass; 17. counting Python's fixture expectations as the product's own proof; 18. weakening a limit constant to make a fixture pass; 19. reporting recovery for bytes that were never restored; 20. equating a merge with inclusion of uncommitted work.

Modal shortcut: **guarding only file entries**. It fails because a slash-suffixed entry can carry arbitrary compressed data and the loop advances with `closeEntry()` after skipping it, so neither the per-part nor the aggregate counter sees those bytes. The executable falsifier is a valid DOCX/XLSX with a `payload/` entry of part-limit+1 bytes; the pinned reader accepts it and the repaired reader must refuse it.

## E. Mechanisms (6 distinct, with artifacts and falsifiers)
1. **Observed baseline**: run the unmodified pinned sources in a fresh JVM on independently built archives. Artifact: `run_r72_office_zip.py` output. Falsifier: baseline not failing the eight-plus directory/duplicate cases. Local gap only.
2. **Unified per-entry accounting**: one capped read loop for files and directories, plus an all-entry name set. Artifact: production Kotlin in both readers. Falsifier: `dir-over`/`aggregate-over`/`duplicate-dir`/descriptor variants, exact and +1. Gap: local.
3. **Independent archive oracle**: Python builds the fixtures (`zipfile`, deflate, data descriptors, corrupt CRC) and re-measures counts, names, sizes and SHA-256 from the archives. Falsifier: forged expectation or tampered fixture. Gap: finite fixtures, not ZIP conformance.
4. **Production import extractor**: execute `Ooxml` on its own boundary set (32 MiB part, 64 MiB total, 5,000 entries, 2 MiB XML, unsafe names). Falsifier: +1 accepted, exact refused, or a traversal name accepted. Gap: local.
5. **Writer resource guard**: early UTF-16 bound before strict XML/UTF-8 work; pinned comparison on the retained Writer corpus. Falsifier: a 25 MiB ASCII string under a 64 MiB heap, and a `é` string whose code units fit but bytes do not. Gap: cannot control allocation before the call.
6. **Compatibility differential**: retained R54–R64 corpora plus python-docx/openpyxl readers on the candidate. Falsifier: a single changed byte or lost legacy case. Gap: finite, not Word/Excel.
7. **Android/visual gate**: exact-revision CI plus genuine frames. Gap: globally unavailable here; it is the reason no Class A claim is made.

## F–J. Artifacts, adversaries, verification, repair, stopping
Every branch above returns executable code or a measured counterexample; no branch is closed by assertion. The strongest adversary per candidate is derived from its own structure: for mechanism 2, an archive whose *only* oversized content is a directory, whose names collide only as directories, whose size is declared in a data descriptor, or whose total crosses the cap in the final entry. Verification binds claims to `kotlinc -Werror` exit status, JVM process exit/output, independent Python inspection with pinned reader versions, and the discovery runner's programmatic rejection of skips. A repaired candidate inherits no trust: all affected suites are re-run and new attacks target the patch itself.

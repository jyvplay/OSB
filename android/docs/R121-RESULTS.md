# R121 — `BESSELK` / `BESSELY`, the Bessel functions of the second kind

`FormulaEval.kt` could evaluate `BESSELJ`/`BESSELI` — and could not evaluate `BESSELK` or
`BESSELY`, the names Excel's own function reference documents for the Bessel functions of the
second kind. A measured check across `FormulaEval.kt` (`grep` for each quoted name, `*.kt`
outside `build/`) returned **zero** dispatch occurrences for both names, so no other site
covered them. Every one of them returned `#NAME?` from a formula.

R121 adds the two names: **+1 dispatch branch (two names) and 9 helpers (`bessh`, `bessk0`,
`bessk1`, `besskSeries`, `besskAsymp`, `bessk`, `bessySeries`, `bessyAsymp`, `bessy`) in**
**`FormulaEval.kt`** (`x` must be > 0 and `n` must be >= 0, else `#NUM!`; wrong arity is
`#VALUE!`) and **+2 lines in**
**`SpillSheetEngine.kt`** (both names in the OOXML export prefix list, because Excel stores
future-function names with the `_xlfn.` prefix). No build file, no Android source, no existing
function is modified. The `besselSeries` kernel and the `BESSELJ`/`BESSELI` branch are pinned
unchanged by rule R121-7, because they are the kernels this round reuses, not its subject.

The math: below `x = 10` the convergent DLMF series is accurate to 1e-12 for both families;
above it the DLMF asymptotic takes over, so both stay positive and finite at arbitrarily large
`x` (the series alone turns negative above x ~ 12). `K_n` uses forward recurrence
`K_{i+1} = K_{i-1} + (2i/x)K_i`, which is stable for `K` (backward recurrence is not — tried,
rejected). The asymptotic term recurrence `term *= (4n^2-(2k-1)^2)/(8kx)` avoids the
coefficient overflow that naive DLMF evaluation hits at x >= 100. Mirrors
`tools/r121_bessel_proto.py`, verified there in pure `math`.

## A. Formal model

**Admissible objects.** Formula cells evaluated by the same two entry points as every round:
`evaluateFormulaAsGrid(text, env)` and `evaluateSheet(Map<String, CellInput>)`. Arguments
arrive as `CellValue` (`Num`, `Text`, `Bool`, `Empty`, `Err`). Domain: `x > 0`, order `n >= 0`
(else `#NUM!`); arity exactly 2 (else `#VALUE!`). Total on the declared domain, with declared
refusals outside it.

**Information/access model.** The evaluator sees only the cell values in `env` and the parsed
AST. It has no clock, no locale, no host function table beyond `kotlin.math`.

**Resource counted.** Nothing is bounded by this round: these are total scalar functions with
declared refusals. The counted quantities are *correctness* quantities — the domain refusals,
the recurrence identities each family satisfies, and the numeric difference from an
independent implementation.

**Success and failure, quantifier order.** For the numeric cases: **for every** probe in the
corpus, the value `E` the engine returns satisfies `|E − R| ≤ 1e-12 · max(1, |R|)`, where `R`
is the documented definition recomputed independently in `tools/gen_r121_bessel_corpus.py`.
For the refusals: **for every** declared out-of-domain input, the engine returns exactly the
declared literal (`#NUM!`, `#VALUE!`) and never a number. The recurrence identities are
structural controls: `K_{i-1}(x) − K_{i+1}(x) = −2i/x·K_i(x)` and
`Y_{i-1}(x) + Y_{i+1}(x) = 2i/x·Y_i(x)` at x = 1, 2, 5, 10 and beyond the crossover at
x = 11, 20, 50.

**Parameters, boundary conditions, units, tolerances.** Order `n` is truncated toward zero to
an integer (Excel truncates). Tolerance `1e-12` relative with an absolute floor of `1e-12` for
the corpus test (values near 1e-219 at x = 500 are compared against the absolute floor). The
crossover x = 10 is exact: series below or equal, asymptotic above; in the overlap both are
transitioning, so agreement there is only checked loosely (1e-3).

**Adjacent problems that must not be substituted.** Excel's display (number formats),
`BESSELK`/`BESSELY` with complex arguments (Excel's are real-only), negative orders (Excel
refuses), `BESSELJ`/`BESSELI` (already present, untouched), and every Class A question.

## B. Outcome space

* **H+** — both names become reachable from both evaluator entry points, keep the declared
  domain and refusals, agree with an independent implementation on 122 probes (110 numeric,
  12 refusals), 14 JUnit cases, 7 gate rules and a byte-identity check on the corpus. **This is
  what happened**, modulo the CI evidence limits in §H.
* **H−** — impossible to *pass* this contract by adding names alone: a name that dispatches to
  the wrong kernel (`BESSELK` returning the series value at x = 500, which is negative) fails
  the corpus; a corpus generated by the code under test fails the meta-control (R121-5).
* **H∂** — the boundary surface: `x ∈ {0, −1}` → `#NUM!`; `n = −1` → `#NUM!`; arity 1 or 3 →
  `#VALUE!`. The corpus encodes all of them.

## C. Frontier

The frontier here is the definition of each function: `BESSELK` is the modified Bessel
function of the second kind (`K_n`), `BESSELY` is Bessel's equation's second solution (`Y_n`),
each for real `x > 0` and integer `n ≥ 0`. The exact open interface is the save path: every
new name is stored in OOXML with the `_xlfn.` prefix (XlsxWriter 3.3.3 `FUTURE_FUNCTIONS`
table, verified earlier by reading `xlsxwriter/worksheet.py` on `pypi.org`). The gate pins
both sides of that interface: dispatch presence and export-prefix presence (R121-1).

## D. Negative space (≥15 shapes that look like a solution and are not)

1. Dispatching `BESSELK`/`BESSELY` but only implementing the series (K goes negative above
   x ~ 12; corpus probes at x = 10 catch the onset, the asymptotic must take over at 10).
2. Implementing the asymptotic with the naive DLMF coefficients (overflows to `nan` at
   x ≥ 100; the term recurrence fixes it).
3. Running backward recurrence for `K_n` (unstable — wrong-sign/magnitude results for n ≥ 1;
   forward recurrence is stable for `K`).
4. Forgetting the k = 0 term (= 1.0) in the asymptotic sum (the sum collapses to ~−1/(8x)
   instead of ~1; caught by the large-x positivity check).
5. Returning a number for `x <= 0` or `n < 0` (both are `#NUM!`).
6. Loosening `TOL` above `1e-12` (fails R121-6).
7. Generating the corpus from the Kotlin kernels (a transcript, not an oracle — detected by
   R121-5 byte-identity and by the gate recomputing each row from `gen_r121_bessel_corpus.py`).
8. Hand-editing the corpus after generation (fails R121-5).
9. Adding names to the dispatch but not the corpus (unmeasured behaviour — fails R121-2).
10. Adding names to the corpus but not the dispatch (the test reads names it never evaluates
    — the reachability test has two probes that would fail in CI).
11. Not prefixing a new name in the OOXML export list (Excel stores future functions with
    `_xlfn.` — fails R121-1).
12. Reusing the series at x = 100 (division-free, but the series diverges past x ~ 12 through
    catastrophic cancellation — the dispatch crossover at 10 is mandatory).
13. Treating `BESSELY` like `BESSELK` (Y oscillates and changes sign; K stays positive).
14. Using `assertEquals` on doubles without tolerance (flaky at last-ULP — the test uses
    `abs(got − want) ≤ TOL · max(1, |want|)`).
15. Dropping the refusal rows from the corpus (fails R121-2's five-refusal minimum per name).

The modal shortcut is D.7: a fixture generated by the code under test. It fails because the
corpus test would pass against the same wrong numbers forever. R121-5 detects it.

## E. Mechanism portfolio (four distinct, kept independent until judged)

1. **DLMF convergent series below x = 10** (chosen). Central construction: `K_0` and `K_1`
   from DLMF 10.31/10.32 via `besselSeries(..., modified = true)`; `Y_n` from DLMF 10.8.1 via
   `besselSeries(..., modified = false)`; `K_n` for n ≥ 2 by forward recurrence. Proved:
   every numeric corpus row at x ≤ 10 agrees with the generator to 1e-12, and the K/Y
   recurrence identities hold to ~1e-14. Cheapest falsification: `K_0(1)` must be
   0.4210244382407083. Gap: local (no Kotlin compiler; CI is the sole compiler — disclosed in
   §H).
2. **DLMF asymptotic above x = 10** (chosen). Central construction: DLMF 10.40 for `K`,
   DLMF 10.17 for `Y`, term recurrence `term *= (4n^2-(2k-1)^2)/(8kx)` with optimal
   truncation, no overflow at any x. Proved: `K_0(500)` = 3.99e-219 (positive, finite),
   `K_0(1000)` underflows to 0.0 (never negative). Gap: local.
3. **Refusals** (chosen). `x ≤ 0` or `n < 0` → `#NUM!`; arity ≠ 2 → `#VALUE!`. Proved: all
   12 refusal rows in the corpus, plus explicit JUnit cases. Gap: local.
4. **Series everywhere** (rejected). Diverges through cancellation past x ~ 12 and goes
   negative for `K` — the asymptotic is mandatory above the crossover.

## G. Second-order adversary

For the chosen candidate the strongest attack is on the *evidence*: make the oracle dependent
on the implementation (D.7), make the tolerance hide a sign error at large x (D.6), or make
the fixture unreproducible (D.8). All three are now controls. The second strongest is the
sign attack: `BESSELK` implemented as the raw series passes every small-x check but returns
negative values at x = 500 — hence the positivity/finiteness case at x = 500 and the
asymptotic branch. The third is reachability: a name can compile and dispatch and still be
unreachable from a cell — hence the two-probe reachability test and the `evaluateSheet`
case. The fourth is the save path: a name can evaluate correctly and still be written with
the wrong prefix — hence R121-1's prefix check, backed by the XlsxWriter table.

What this adversary does **not** touch: Excel's own last-ULP values (out of scope, stated),
and a shared bug between generator and gate (they are the same `render()` — R121-5 guards
reproducibility, not independence; the Kotlin test in CI is the independent check against the
fixture).

## I. Repair: a candidate inherits no trust

Three failures occurred, all in my own evidence machinery, not in a hidden requirement:

1. **The asymptotic sum dropped the k = 0 term (= 1.0) in both the Kotlin port and the Python
   generator.** `K_0(500)` came out −9.97e-223 (negative, wrong magnitude) instead of
   3.99e-219. Fixed by initializing the sum to 1.0 in `besskAsymp`/`bessyAsymp` and in
   `gen_r121_bessel_corpus.py`; the large-x positivity check now passes.
2. **Two hardcoded reference values in the Kotlin test were wrong.** `K_0(2)` was asserted
   against 0.1138938827389664 (the oracle says 0.1138938727495336) and `Y_0(2)` against
   0.5103756676150117 (the oracle says 0.5103756726497453). Corrected both to the
   oracle values before any run could pass against them.
3. **The gate's dispatch check counted `bessk` once but the text `private fun bessk` also
   matches `bessk0`/`bessk1`/`besskSeries`/`besskAsymp`;** likewise `bessy`. Fixed by counting
   `private fun bessk(`/`private fun bessy(`. After each repair the whole local lane, the
   census, the gate and the generator were re-run on the repaired tree.
